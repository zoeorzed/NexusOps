# 业务场景验证的复现与判分

本验证补充真实 `/chat` 链路和知识检索的业务证据。数据位于 [`business-scenarios-v1.json`](../evaluation/business-scenarios-v1.json)：12 条对话请求、10 条独立检索请求，全部使用合成用户、订单和演示知识。它是开发回归集，未混入冻结的 95 条单标签意图评测，也没有独立人工盲标，结果不能表述为生产问答正确率。

## 覆盖范围

| 维度 | 场景 | 判定方式 |
| --- | --- | --- |
| 复合诉求 | 闪退与多扣款、配送与退款、陌生设备登录与无法登录、发票更正与转人工 | 路由/升级标记检查，另逐条复核内容覆盖 |
| 知识及执行边界 | 退款审核与到账阶段、缺失的发票规则、直接要求打款、500 故障 | 依据参考文档核对，检查是否编造规则或后台执行 |
| 会话 | 同会话承接订单、同用户新会话、不同用户复用会话 ID | 当前/解析实体字段与自然语言分别核对 |
| 检索 | 8 条有答案、2 条无答案问题 | 有答案计算 Hit@3/MRR@3；无答案单独复核 |

账户安全与无法登录均属于 Technical 可处理范围，不能仅为获得双 Agent 路由而强制要求 Billing。开发首轮曾把此场景写为 Technical + Billing；确认领域语义后修正为 Technical，并继续要求回答覆盖账户保护与登录恢复两项诉求。首轮失败证据与最终运行应分别保留。这项修正属于开发预期校正，不应包装成独立盲测成绩提升。

## 运行方式

先完成 Java 构建，启动专用 Redis 和项目服务。使用已有的模型配置，设置 `LLM_FALLBACK_ENABLED=false`，令 `ECHOMIND_DATA_DIR` 指向一个新建的空目录，并将服务绑定本机接口。显式设置实际 Redis 地址及密码。不要使用已有演示服务的数据目录：采集器要求初始库恰好为 6 个默认 chunk，随后只导入一次 `demo/knowledge.json` 的 2 个补充 chunk。

服务就绪后，在项目根目录运行：

```powershell
python demo/run_business_validation.py --base-url http://127.0.0.1:8080 --output evaluation/results/business-new-run.json
```

输出路径必须是新的文件，采集器拒绝覆盖。默认每个 HTTP 请求超时 180 秒，可用 `--timeout-seconds` 调整至 1–600 秒；这不是整个场景的总时限。脚本先完成 10 条 `/search`，再运行 12 条 `/chat`，逐条写入原始响应、Trace、客户端耗时与结构检查。每次生成新的合成用户/会话后缀，记忆用例仍按协议共享同一组标识。

该命令会调用配置的模型并产生 API 用量。采集器不加载或输出密钥；仍应使用合成材料，并审阅待公开的证据文件。成功退出仅代表结构检查全部通过且检索 HTTP 请求未记录失败，**不表示所有回答正确**。回答内容审查状态始终保留为待复核，需在独立的审查记录中说明结论、依据和审查者身份。

只测试采集器的计算和协议，不访问服务或模型：

```powershell
python -m unittest discover -s demo -p test_business_validation.py -v
```

## 检索统计规则

8 个有答案问题各自给定参考文档 ID。参考目录覆盖全量 6 个默认文档和 2 个补充文档，实际检索范围同样是全库。文档 ID 由当前单 chunk 规则计算，但命中必须同时核对实际返回的 **ID、标题、原文和 chunk 编号**；仅计算出正确 ID 不构成成功验证。结果保留逐文档的目录核对记录，未在响应中观测到的文档不能声称已核对。

- `Hit@3 = 前三位中存在已核对相关文档的有答案题数 / 8`。
- `MRR@3 = Σ(首个已核对相关文档实际排名的倒数；未命中为 0) / 8`。
- 请求失败、缺失响应、非法 `results` 结构保留在 8 题分母，按未命中计。
- 从 `assessment_version=2` 开始，排名严格使用 HTTP 返回位置；重复、无效及原文不符项仍占位置，不先删除再提升后续结果的排名。
- 出现显式 fallback 文档时，该请求不计命中。保留 fallback 观察，不能用兜底文本代替知识命中。
- 两个无答案问题不进入上述分母，也不要求空列表。系统可能返回相似但无法回答的文档，需单独复核其相关性。生成回答的边界由配套的缺失发票政策 `/chat` 用例检查；航空里程题仅测试检索，没有进行回答生成测试。

`/search` 含查询改写、重排及本地 BM25 + hash vector 检索。其返回不暴露改写错误或完整工具状态，`reranked=false` 不能独立判定调用失败。这些独立请求也不等于 `/chat` 当轮注入的上下文；当前 Trace 没有引用文档 ID，因此本测试不能给出真实回答逐句引用准确率。

## 对话结构检查与内容复核

结构检查核对请求/会话/Trace 标识、预期领域参与、升级标记、检索工具报告状态、Agent 执行失败和实体继承。工具报告成功仍不能替代内容复核。`intent_source_scores.llm` 记录模型侧置信度，零值也可能来自识别异常后的兜底；接口未暴露明确失败标记，不能仅凭零值统计调用失败。`verified`、`grounded` 是模型判断，不是独立业务真值。

逐条内容复核需对照数据集 `content_criteria` 和冻结参考原文：是否覆盖全部诉求，退款审核 1–3 个工作日与审核通过后到账 5–7 个工作日是否区分，缺失规则时是否承认未知，是否误称已查流水/退款/开票/建单/接通真人。不要仅用关键词命中或另一模型自评分宣布业务通过。由 AI 助手完成的复核应明确标注，不称为独立人工验收。

开发首轮仅检查同用户新会话的近期实体解析不自动继承旧订单，允许长期记忆召回。第二轮结构检查通过，内容复核却发现画像将旧订单、退款意愿用于当前请求，说明单靠提示词和实体字段检查不足。现版 `/chat` 将生成上下文限制为当前会话消息与摘要；跨会话摘要和画像仍保存，但不自动注入当前业务回答。新会话及无订单号的 500 用例增加自然语言中不得出现旧订单号的回归检查，旧轮次数据与结果单独保留。

不同 `user_id` 复用同一个 `conv_id` 的用例检查标识维度下是否串单；当前 `user_id` 由客户端提供，这不证明身份认证、权限控制或抵抗身份冒用。当前会话压缩摘要仍可使用，这次变更不删除历史数据；跨会话作答需要另行设计用户确认和事实归属机制，不能宣称本轮已实现。

每轮报告应同时记录应用提交/构建标识、模型与关键配置、数据集及采集器 SHA256、运行时间、全部失败与局限。若仅修正统计逻辑，可依据已经保存的原始响应另存离线重评文件并记录评估版本，不覆盖原始证据，也不需要为了重算指标再次调用模型。
